**Chart/navigation TypeScript review — 2026-09-21**

**Implementation completed locally — 2026-09-21**

The seven cleanup areas below are implemented in `zlayers` and `faa-regs`. The affected navigation, procedure catalog and Chart Supplement products were rebuilt for 2026-09-03. No raster rebuild or hosted deployment was performed. Existing uncommitted work was preserved.

- Publisher and client now share explicit versioned identity, capability and coverage contracts. Current terminal publications require both approaches and coded SID/STAR data; same-count changes fail the publisher's JSON identity check. Legacy documents retain a separate compatibility path.
- NASR ingestion validates required headers, nonempty national tables and every row's edition, records deliberate exclusions, and rejects empty core navigation exports.
- Chart Supplement catalogs retain the FAA's complete expected airport inventory independently of available books. A missing applicable region or missing supplement snapshot prevents a regional download from being marked complete.
- Navigation and TPP products use immutable content filenames and atomic manifest replacement. Interrupted publication leaves the previous generation readable. PDF indexing is reused when the source XML bytes and books are unchanged, including local versus remote XML reads and UTF-8 BOM normalization.
- Shared indexes replace repeated national terminal-leg scans. Saved synthetic fixes still require exact source membership and coordinates. The one-airport resolver measurement fell from 141 ms / 16.9 MiB to 4.67 ms / 0.61 MiB on first terminal use and 0.058 ms with the index shared. These are single local Node measurements excluding JSON loading, not mobile performance claims.
- Explicit NASR/CIFP selections migrate at the saved-data boundary. Source adapters feed one terminal composition boundary for children, ownership, connectors, gaps and distances. The three pickers share resource loading and preview lifecycle. Existing geometry interpretation and its diagnostics remain intact.
- All 26 reviewed approach-title exceptions moved out of browser code into dated publisher data. Generated associations pin the exact terminal, CIFP and chart XML identities. Distinct parallel-runway choices remain explicit; unmatched charts retain their plates and coded procedures remain directly selectable.

Validation passed: 1,306 client unit tests plus the new indexing regression; 186 publisher tests plus 13 focused procedure tests after the final cache fix; TypeScript/import checks; production build; publisher-to-client negative fixtures; and 163 route/offline browser cases after correcting five obsolete fixture expectations. The rebuilt national artifacts also pass the actual client resource guards.

The national export accounts for all 201,076 terminal primary legs and 6,744 continuation records: 10,234 approaches, 2,193 coded SIDs and 1,916 coded STARs. All 5,292 expected Chart Supplement airport entries are available across nine books. KVGT ILS/LOC 12L is associated with `KVGT:I12L` and has a selectable entry.

This cleanup does not establish ForeFlight feature parity or remove source and geometry limitations. The national audit still identifies two unresolved source references, 294 terminal choices requiring geometry review, and seven distinct feeder starts that are not offered. Of 11,089 instrument chart records, 9,184 have selectable coded associations; 1,905 remain unmatched for the recorded source/scope/review reasons. The implementation does not silently substitute another procedure for those charts.

Commands, exact identities, test results and national audit summaries are retained in [implementation evidence](../evidence/chart-nav-review/2026-09-21/implementation/README.md). Both the original route-history generation and the separately refreshed local generation remain available as immutable artifacts; their source differences are recorded there.

**Original review**

Recommendation: retain the chart delivery, verified storage, and map lifecycle foundations. Fix the publication contracts first, then consolidate terminal procedure selection and route composition. A ground-up rebuild is not justified by this review. There are concrete completeness defects, and the recent terminal expansion added a parallel runtime path that deserves consolidation before more procedure features are added.

This review covers the current working trees in `zlayers` and sibling `faa-regs`, including the uncommitted terminal work. No production code was changed for this review. The findings below distinguish reproduced defects from design recommendations.

**1. High priority: the client does not enforce the publisher's terminal coverage or content identity.**

Relevant locations:

- `faa-regs/download-nasr.ts:449`: publishes terminal file size, SHA-256, and coverage.
- `zlayers/src/workspace/catalog/catalog.ts:244`: reduces this to the NASR procedure count and a timestamped URL.
- `zlayers/packages/contracts/src/terminal-procedures.ts:57`: accepts absent approaches and coded SID/STAR families; it does not enforce the publisher's root schema version.
- `zlayers/src/core/data/references.ts:44`: validates that permissive shape, the NASR count, and an optional locally captured JSON identity.

Reproduction using the built 2026-09-03 edition: the manifest advertises 10,234 approaches. Removing both `approaches` and `codedProcedures` from the document, while retaining its NASR procedures and metadata, still passes the client document guard. A legacy document with the same edition and NASR count is also eligible. A newer manifest paired with stale or partial same-cycle JSON can therefore restore the original missing-procedures symptom.

The `?v=` query is a cache key; it does not make a mutable server path immutable. Capturing a local JSON hash after accepting the document pins the accepted bytes, but does not establish that they match the publisher's intended export.

Fix: define a versioned product contract containing identity, required capabilities, and counts. Carry it through catalog discovery, loading, offline capture, and readiness checks. Treat legacy formats as explicit versions with known capabilities. Current exports must require the advertised families. Define the digest representation explicitly: the publisher's file hash and the client's `JSON.stringify` hash are different representations and cannot simply be assigned to the same field.

Acceptance: real publisher output passes the consumer guard; removing a required family, changing a same-count record, or substituting another same-cycle build fails before caching or activation. Legacy fixtures remain readable under their own contract.

**2. High priority: general NASR ingestion can silently publish empty core navigation products.**

Relevant locations: `faa-regs/lib/nasr.ts:99`, `:113`, `:296`, `:371`, and `:408`.

`buildNasrProducts` checks some FRQ/PFR requirements, but does not apply equivalent header and nonempty-table contracts to all required inputs. Its effective-date check gathers nonempty dates across tables. Missing coordinates return `null`, and `flatMap` drops those records without an exclusion ledger.

Two probes used copies of the real 2026-09-03 CSV inputs:

| Input mutation | Baseline output | Mutated output | Build result |
| --- | ---: | ---: | --- |
| Rename APT_BASE's `LAT_DECIMAL` header | 19,411 airports | 0 airports | Success |
| Replace FIX_BASE with its header only | 70,089 fixes | 0 fixes | Success |

The complete build subsequently publishes these returned products and derives manifest counts from them. Thus a count check against that manifest cannot detect the omission.

Fix: a small shared CSV boundary helper should validate required headers, required table presence, and each row's edition. Reconcile source rows with exported rows and explicit exclusions. Preserve legitimate records with unavailable coordinates in an exclusion ledger; distinguish that case from an absent schema column. Reuse the accounting approach already present in `terminal-bundle.ts`. Do not hard-code this cycle's national totals as permanent requirements.

Acceptance: missing required headers and empty required national tables stop publication. Every intentionally omitted row has a reason. Failed validation leaves the previous published generation available.

**3. High priority: offline completeness does not detect an entirely missing Chart Supplement region.**

Relevant locations:

- `faa-regs/build-chart-supplements.ts:42`: deliberately supports partial regional builds.
- `zlayers/src/layers/plates/offline.ts:38` and `:54`: derive required supplements only from the airport records that survived publication.
- `zlayers/src/offline/plan-records.ts:27`: checks books named by a snapshot, but accepts the absence of that snapshot.

Reproduction: remove the Southwest volume and its airport entries from the otherwise valid national supplement catalog, then plan California with the full airport and TPP data. The supplement catalog still passes validation. The planner omits both `cs-sw.pdf` and the `chart-supplements` reference, and `snapshotFilesIncluded` returns true. The readiness path has no remaining supplement expectation to check. Other files can finish successfully despite this missing required product.

Partial publication itself is useful. The defect is losing the distinction between “not published in this build” and “not applicable to this region.”

Fix: publish expected and available coverage from the FAA supplement index, including missing volumes/targets. Require that coverage when constructing a complete regional download. Determine applicability from the FAA index, not an assumption that every NASR airport must have a supplement entry. Continue allowing partial catalogs for browsing, with explicit availability.

Acceptance: a missing Southwest book prevents California from being declared complete; an unrelated missing region does not prevent downloading a covered region.

**4. Medium priority: directory replacement is recoverable on exceptions, but is not an atomic publication.**

Relevant location: `faa-regs/lib/fs-utils.ts:54`; used by the navigation and TPP builders.

`replaceDirectoryAtomically` first renames the live directory to a backup, then renames staging into place. A reader can observe the gap. A process exit between the two operations bypasses the rollback code.

A child-process probe against disposable `/tmp` directories exited immediately after the first successful rename. Result: the canonical `nav/` directory was absent; only `nav.previous-*` and staging remained. This does not establish that a deployed incident has occurred. It demonstrates an interrupted-build failure that the current helper cannot prevent.

Fix: write immutable generation/content files, then atomically replace one small manifest/pointer. Keep the prior generation until retention cleanup. The chart packager already provides a useful local example of publishing content before its manifest. This also allows old saved references to retrieve their actual bytes after a same-cycle rebuild.

Acceptance: interrupt before and after each publication step; readers always get a complete old or new generation. Throw/rollback tests alone are insufficient.

**5. Medium priority: airport previews rebuild national terminal indexes on the main thread.**

Relevant locations: `packages/domain/src/route.ts:63`, `:70`; `src/layers/routes/approach-picker.tsx:80`, `departure-picker.tsx:55`, and `terminal-picker.tsx:48`.

Each picker directly constructs a resolver. Even when its airport collection contains only the selected airport, the resolver walks all national approach and SID/STAR legs and creates pinned fix features. React memoization avoids doing it on every render, but a newly mounted picker constructs it again. The separate `routeResolver` cache used by the route plan does not serve these calls.

One Node 24 measurement using the built edition, excluding JSON loading:

| Resolver inputs | Construction | Retained heap increase |
| --- | ---: | ---: |
| National navigation plus terminal data | 378 ms | 36.4 MiB |
| One airport plus national terminal data | 141 ms | 16.9 MiB |
| One airport without terminal data | <1 ms | approximately 0 MiB |

These are single local measurements, not browser or mobile benchmarks. The national traversal is directly visible in the code; the measurements establish its material cost in this environment.

Fix: prepare immutable terminal indexes once per document identity, and separate those indexes from selected-route interpretation. Airport previews should use the selected procedure or share the prepared indexes. Keep exact pins and coordinate-qualified identities. Adding another cache of whole resolvers for each airport would retain avoidable data.

**6. Design recommendation: consolidate terminal composition and the picker workflow.**

Current structure:

- NASR filing topology is expanded by `terminal-procedures.ts` and legacy departure attachments.
- CIFP SID/STAR paths use `coded-terminals.ts`, fabricate an approach-shaped input with `transitions: []` and `final: path.legs`, then modify the route plan.
- Approaches use a separate attachment expander that modifies the plan again.
- `route.ts:153` sequences those mutations; ownership, connectors, waypoint ordering, and editing rules must agree across them.
- The three pickers repeat resource loading, stale-result handling, retries, catalog association, preview setup, and commit behavior.
- `RouteDeparture` represents both SID and STAR selections; `ApproachLeg`, `ApproachPreview`, and `approachDepictions` also carry departure/arrival behavior. Consumers compensate with additional shape checks and restrictions.

This is the main area where a focused rewrite is warranted. The problem is multiple representations and owners of the same behavior, rather than individual file length.

Use explicit source adapters and one terminal composition boundary:

1. Preserve NASR filing topology and CIFP coded legs as distinct inputs with explicit capabilities. NASR must not acquire invented geometry merely to fit a common interface.
2. Introduce a terminal selection union with source, edition, airport, procedure, branch, and kind. Adapt old saved selections once at the persistence boundary.
3. Reuse the existing fixed/schematic/gap span model as the geometry result. Keep source references, constraints, phase, open endings, and diagnostics attached to spans.
4. Compose the selected terminal spans and enroute route in one place with explicit connection rules and stable ownership. Renderers, distance calculations, and edit actions consume that result.
5. Share picker resource state, preview lifecycle, and commit rules. Retain small family-specific controls for runway/transition/entry choices.

Keep the existing geometry algorithms while changing these boundaries. The interpreters contain real procedure semantics and documented schematic policies; replacing them all at once would discard useful evidence. Centralize display tolerances and fallback policies, and require fixtures and national audit evidence for changes. Avoid an extensible plugin framework or a class hierarchy for leg handlers.

Acceptance should cover behavior across products: SID → airway, airway → STAR, STAR → approach with a shared fix or explicit gap, vectors, missed paths, stale saved selections, preview/committed-route agreement, and editing without flattening a curved or discontinuous procedure into straight lines.

**7. Design recommendation: move edition-specific chart associations into published data.**

Relevant location: `packages/domain/src/approach-matching.ts:47` and `:76`.

The browser contains a reviewed airport/title/route table gated on the literal date `2026-09-03`. Its conservative matching is useful, but preserving these associations in another cycle currently requires a code release. This is a concrete example of data maintenance becoming application patching. The associations also span the independently maintained chart and coded-procedure products.

Generate a plate-to-coded-procedure association artifact during publication, with edition, source identities, matching rule, ambiguity/unmatched status, and evidence for reviewed exceptions. Keep ambiguous associations explicit. The client should display those associations and continue offering unmatched coded procedures directly. Do not make title matching progressively more permissive or copy the current exception table into every future edition.

**Implementation order**

1. Add publisher-to-consumer contract fixtures and the four reproduced negative cases. Establish required capabilities and coverage in the published envelopes.
2. Enforce NASR input accounting and regional supplement expectations; publish immutable generations through a single commit point.
3. Consolidate terminal selections, prepared indexes, and route composition while retaining the existing leg interpreter and golden fixtures.
4. Consolidate picker resource/preview state, move chart associations into edition data, and remove runtime compatibility branches only after migration tests pass.

Use independently reviewable changes. Rebuild only affected navigation/catalog products while their contracts evolve; raster chart rendering does not need to be repeated for these fixes.
